# План тестирования (Test Plan)
**Проект:** `property-view-api` (RESTful API и веб-клиент каталога отелей)  
**Версия:** 1.0  
**Дата:** 2026-10-26  
**Связанная спецификация:** [docs/SRS.md](SRS.md)

## 1. Цель тестирования
Целью тестирования является комплексная проверка соответствия веб-приложения `property-view-api` бизнес-, пользовательским, функциональным (`FR-01`..`FR-18`) и нефункциональным (`NFR-01`..`NFR-07`) требованиям, зафиксированным в [SRS.md](SRS.md), выявление дефектов до ввода системы в эксплуатацию, подтверждение корректности переходов жизненного цикла сущности `Hotel`, отсутствия уязвимостей контроля доступа (IDOR, неавторизованный доступ, утечка стектрейсов) и оценка способности системы выдерживать целевую и пиковую пользовательскую нагрузку.

## 4. Критерии тестирования (выраженные через метрики)

1. **Критерии начала тестирования (Entry Criteria):**
   - Проект собирается командой `mvn test-compile` без ошибок компиляции (`100%` успешная сборка).
   - Приложение успешно запускается на порту `8092`, миграции Liquibase (`001`, `002`) применяются без ошибок, эндпоинт `GET /property-view/hotels` возвращает HTTP `200 OK`.
   - Утверждена спецификация требований [SRS.md](SRS.md) (`18 FR` и `7 NFR`).
2. **Критерии приостановки тестирования (Suspension Criteria):**
   - Обнаружен блокирующий дефект (`Blocker`), препятствующий запуску приложения, применению миграций БД или выполнению более `30%` тест-кейсов.
   - Доля неуспешных смоук-тестов (`scripts/smoke.sh`) превышает `0%`.
3. **Критерии возобновления тестирования (Resumption Criteria):**
   - Блокирующий дефект устранён, сборка и `scripts/smoke.sh` проходят на `100%`.
4. **Критерии завершения тестирования (Exit Criteria) и Приёмочные критерии (Acceptance Criteria):**
   - Процент выполнения запланированных тест-кейсов ($P_{exec}$) = **`100%`**.
   - Покрытие функциональных требований тест-кейсами ($C_{req}$) = **`100%`** (для всех `FR-01`..`FR-18`).
   - Процент успешного прохождения тест-кейсов ($P_{pass}$) >= **`95%`** (все непрошедшие проверки задокументированы в [ISSUES.md](../ISSUES.md) с анализом важности и обходных путей).
   - Покрытие продуктового кода автотестами по JaCoCo (`Instruction` и `Line` Coverage) >= **`70%`** (фактически достигнуто **`96.92%`**).
   - Количество открытых дефектов уровня `Blocker` = **`0`**, количество нарушений статического анализатора Checkstyle = **`0`**.

## 5. Метрики качества и тестирования (с формулами и расчётом)

### 5.1. Процент выполнения тест-кейсов ($P_{exec}$)
$$P_{exec} = \frac{N_{executed}}{N_{total}} \times 100\%$$
- $N_{executed} = 30$ (выполнено тест-кейсов из [TEST_CASES.md](TEST_CASES.md))
- $N_{total} = 30$ (всего разработано тест-кейсов)
- **Расчёт:** $P_{exec} = \frac{30}{30} \times 100\% = \mathbf{100.0\%}$

### 5.2. Процент успешного прохождения тест-кейсов ($P_{pass}$)
$$P_{pass} = \frac{N_{passed}}{N_{executed}} \times 100\%$$
- Из 30 выполненных системных тест-кейсов:
  - $N_{passed} = 29$ (успешно пройдены в штатном режиме);
  - $N_{failed} = 1$ (`TC-29` — воспроизведение конкурентной гонки при одновременном создании нового удобства `DEF-01`).
- **Расчёт:** $P_{pass} = \frac{29}{30} \times 100\% = \mathbf{96.67\%}$ (превышает целевой порог `>= 95%`; по 134 модульным/интеграционным JUnit-тестам $P_{pass} = \frac{134}{134} \times 100\% = \mathbf{100.0\%}$).

### 5.3. Покрытие требований тест-кейсами ($C_{req}$)
$$C_{req} = \frac{R_{covered}}{R_{total}} \times 100\%$$
- $R_{total} = 25$ требований (`18 FR` + `7 NFR` в [SRS.md](SRS.md))
- $R_{covered} = 25$ требований покрыты тест-кейсами и автотестами (см. [TRACEABILITY_MATRIX.md](TRACEABILITY_MATRIX.md))
- **Расчёт:** $C_{req} = \frac{25}{25} \times 100\% = \mathbf{100.0\%}$

### 5.4. Процент устранения дефектов и нарушений по важности ($D_{fixed}$)
$$D_{fixed, S} = \frac{D_{resolved, S}}{D_{found, S}} \times 100\%$$
- **Нарушения статического анализа и безопасности / авторизации (`FR-17`, Checkstyle):** найдено `9` нарушений Checkstyle + `2` пробела безопасности (отсутствие защиты управления отелем и операционного логирования) $\rightarrow$ устранено `11` из `11` ($\mathbf{100.0\%}$).
- **Архитектурные и функциональные расхождения в реестре [ISSUES.md](../ISSUES.md) (`DEF-01`..`DEF-05`):**
  - `Blocker / Critical`: найдено `0` ($\mathbf{100\%}$ чистота).
  - `Major` (`DEF-01` — конкурентная вставка нового удобства): `1` задокументирован как архитектурное ограничение (`Known limitation` в README и `ISSUES.md`) с рабочим workaround.
  - `Moderate / Minor` (`DEF-02`..`DEF-05`): `4` задокументированы в `ISSUES.md` для бэклога развития.
